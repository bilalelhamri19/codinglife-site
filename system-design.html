1. The Microservices Hype Cycle & Its Silent Victims

Between 2016 and 2022, microservices were pitched as the default architecture for every software startup. Teams of 6 engineers prematurely carved simple CRUD backends into 25 independent services, each with its own repository, database, Dockerfile, and CI pipeline. The result was not agility; it was complete engineering gridlock.

Today, high-profile case studies (including Amazon Prime Video cutting cloud infrastructure costs by 90% by moving from serverless microservices to a monolithic architecture) have catalyzed a pragmatic renaissance: the Modular Monolith.

"If you cannot build a well-structured monolith with clean boundaries in memory, what makes you think you can build a distributed system across unreliable network cables?"

2. The True Operational Cost: The Distributed Systems Tax

Microservices replace in-memory function calls (which execute in nanoseconds) with remote HTTP/gRPC network calls (which take 5 to 50 milliseconds and can fail unpredictably). Every boundary crossing incurs:

  • Network latency and JSON serialization/deserialization CPU overhead.
  • Partial failure handling: retries, exponential backoff, circuit breakers, and idempotency keys.
  • Distributed tracing complexity: passing correlation IDs across multiple services via OpenTelemetry.
  • Loss of ACID database transactions: requiring complex distributed sagas and eventual consistency.

3. What Exactly is a Modular Monolith?

A Modular Monolith is a single deployable artifact (one binary, one database) whose internal code is strictly partitioned into encapsulated domain modules. Module A can never directly query Module B's database tables or import internal classes; communication occurs solely through explicitly exported public interfaces or in-process domain events.

TypeScript / Monorepo — Enforcing Module Encapsulation
// packages/billing/index.ts (PUBLIC API OF BILLING MODULE)
export { BillingService } from './src/BillingService';
export type { InvoiceSummary } from './src/types';

// INTERNAL IMPLEMENTATION (STRICTLY HIDDEN FROM OTHER MODULES):
// packages/billing/src/internal/CreditCardProcessor.ts -> NOT EXPORTED!
// packages/billing/src/internal/billingDb.ts           -> NOT EXPORTED!

4. Enforcing Module Boundaries at Build-Time

Honor systems fail. Enforce boundaries programmatically using tools like Nx, Goodcheck, or TypeScript project references that fail the build if a module imports another module's private internals.

5. The Pragmatic Migration Strategy: Monolith First

Always start with a Modular Monolith. If a specific module (e.g. video transcribing or fraud detection) later demands vastly different hardware requirements (like GPU clusters) or independent scaling, that single clean module can be extracted into an independent microservice in days—not months.

1. هوس المايكروسيرفيس والعودة للواقع

لسنوات طويلة سادت فكرة خاطئة بأن كل مشروع ناشئ يجب أن يقسم إلى 20 خدمة مايكروسيرفيس مستقلة. هذا التعقيد المبكر دمر إنتاجية مئات الفرق البرمجية. اليوم، أثبتت التجارب الكبرى (بما فيها تجربة أمازون التي وفرت 90% من تكاليف السحابة بالعودة إلى المونوليث) أن المعمارية الأذكى هي المونوليث النمطي.

2. ضريبة الأنظمة الموزعة (Distributed Systems Tax)

استبدال استدعاء الدوال السريع في الذاكرة بالطلبات الشبكية عبر HTTP يضيف بطئاً ملحوظاً، ويتطلب إدارة معقدة للمحاولات المتكررة وقواطع الدوائر (Circuit Breakers) وفقدان المعاملات المالية الموحدة ACID.

3. قوة المونوليث النمطي

المونوليث النمطي يعمل كبرنامج واحد وسيرفر واحد وقاعدة بيانات واحدة، ولكن كوده مقسم داخلياً لوحدات وظيفية معزولة تماماً لا يمكن لأي وحدة أن تطلع على البيانات الداخلية للوحدة الأخرى، مما يمنحك سرعة الذاكرة وسهولة التطوير والتوسع.
